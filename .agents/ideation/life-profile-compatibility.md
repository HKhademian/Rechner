# Life Profile compatibility inventory and initial contracts

Status: implementation guidance for step 1 of [the project plan](life-profile-project-plan.md), 18 November 2026. It describes the current checkout and the proposed contracts for the new timeline; it does not claim the new storage or UI exists.

## Current data paths

- The shared v1 Profile uses `rechner:life-profile:v1:profile` (`src/engine/lifeProfile/types.ts`). `readUnifiedLifeProfile` returns an example-filled profile when the record is absent or corrupt; the v1 parser also supplies example values for individual missing or invalid fields and reconstructs any object as version 1. A serialized v1 record does not say which values were explicitly entered. The store persists the entire parsed object after an edit; a saved record is not evidence that every field was confirmed.
- Shared storage follows the active memory, session or persistent mode. Full backup version 2 contains readable entries; version 1 remains importable. `appStorage.ts` lists the v1 Profile among shared backup keys. The backup parser validates the outer structure, key and encoding, but does not validate the shared Profile schema. Restore replaces active records and attempts rollback from an exported snapshot on a storage failure; rollback can itself fail when storage remains unavailable.
- Net Pay's `CalculatorPeriodControl.tsx` sync button writes directly to live year, gross, region, household and tax inputs. Saved comparison scenarios and drafts have separate state. Monthly gross is ordinary pay; annual input is actual modeled annual earnings. Working months and annual salary-payment equivalents affect the schedule, including prorated extras and stated bonus assumptions (`src/engine/tax/employmentPeriod.ts`).
- The parental dashboard sync explicitly writes planning year, gross salaries, existing children and a mapped Kita preset into its own store. It does not transfer life events. Its scenario action batches, month identities, outputs and stored data remain owned by that planner.
- `resolveParameterForYear` uses an annual key and may select the latest prior or earliest available entry, recording projection. It does not alone establish intra-year or jurisdictional applicability. Do not present a fallback as a verified current rule.

## Decisions before new Profile records

1. **Separate record and explicit versions.** Keep the legacy v1 key and behavior for existing consumers. Introduce a distinct, explicitly versioned key for the new people/event model when it is implemented; integrate it with all storage modes and shared backup in the same release. Validate version and schema before constructing new-domain objects. Do not pass new records through the permissive v1 parser.
2. **Legacy values remain ambiguous.** Preserve the original v1 record, including values that happen to equal defaults. Present candidates for review; only explicit confirmation creates a corresponding new fact. Do not manufacture dates, identities or events from defaults, and do not silently change existing calculator inputs.
3. **Unsupported or invalid records are protected.** Distinguish missing, supported, invalid and unsupported versions. Preserve raw unsupported/corrupt records and disable writes that would replace them; offer a clear explanation and a safe export/recovery path. Never fall back to a blank profile and save over the original. Unknown future types must be preserved losslessly or explicitly blocked, not dropped by a serializer.
4. **Restore validates before mutation.** Validate the complete backup and known Profile schemas before any replacement. An unsupported version must not overwrite existing records; reject the restore with an actionable error while preserving its source file. Accept supported v1 and v2 backups; document how an older backup lacking the new key behaves before shipping. Preview replacement scope and protect unrelated data. Take a recoverable pre-restore snapshot and attempt rollback on write failures; if the backend prevents rollback, report failure honestly and provide recovery from the snapshot rather than promising atomicity that browser storage cannot guarantee.
5. **Idempotent migration and mode isolation.** Repeated reads, retries and restore must not duplicate facts or erase legacy data. Verify memory, session and persistent modes, cross-tab refresh and mode transitions. A migration must be reversible via retained original data or backup and must not silently write into a different storage mode.
6. **First Net Pay bridge.** A known gross amount and explicit monthly/yearly basis are previewed as a patch into a named draft or new comparison. Do not touch live inputs or unrelated fields. A midyear change must not turn the current rate into actual annual earnings; verify 13-pay and working-month assumptions. Hours alone do not imply salary.

## Regression cases and baseline

On this checkout, `ASTRO_TELEMETRY_DISABLED=1 DO_NOT_TRACK=1 node --test src/engine/lifeProfile/storage.test.ts src/engine/storage/appStorage.test.ts src/store/calculatorStore.test.ts src/engine/tax/calculatorGrossPeriod.test.ts` passed 30 tests on 18 November 2026. Existing tests cover Profile serialization and mode isolation, old and structured backup round trips, a failed-write rollback, saved Net Pay drafts, working months, salary basis and partial-year extra-pay schedules. They do not establish the proposed new-schema guarantees.

Before the first new persisted person or event, add targeted tests for ambiguous v1 defaults versus edits; absent, corrupt and unsupported versions; unknown event payload preservation; v1 and v2 backup restore with and without the new key; validation before writes; write failure and rollback failure; all storage modes and transitions; idempotent migration and repeat import. Before the handoff, test an hours-only event, a midyear raise, 13 payments, the explicit preview and preservation of live/other scenario inputs. Before parental integration, compare representative existing scenario inputs and monthly results before and after using the new Profile.
